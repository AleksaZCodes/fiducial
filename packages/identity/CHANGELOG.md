# @fiducial/identity

## 0.2.0

### Minor Changes

- ea76c82: Grant storage — where the permission rows live.
  
  `can()` takes a list of grants; this is the half that produces it. A grant is
  one row: principal, resource, role.
  
  - `SqlGrantStore` — a consumer of the `database` contract, not a new contract
    beside it, so it works on D1 today and any future vendor free. Takes the
    database structurally, so this package still depends on nothing.
  - `MemoryGrantStore` — a real implementation for tests and seeded products,
    held to the same suite as the SQL one.
  - `grantsFor` (the read on the authorization path), `grantsOn` (the read a
    sharing UI makes), `grant`, `revoke`.
  
  The table itself is generated by `fid add identity` + `fid derive` from the
  identity model, so its CHECK constraints cannot drift from the `Principal`,
  `Resource` and `Role` variants.
- 614332f: New package: `@fiducial/identity` — one identity model across users, devices
  and services.
  
  `Principal` spans `user`, `device`, `service` and `anonymous`;
  `can(principal, action, resource, grants)` is the whole authorization rule.
  Deny by default, an unidentified principal (anonymous, or an all-zero
  sentinel id) is refused, and a device may read itself without a grant but
  never write itself.
  
  Mirrors the Rust `fiducial-identity` crate, which firmware, the desktop
  backend and the CLI run. Both are held to `docs/identity/vectors.json` — a
  decision table generated from the Rust crate and replayed here — because an
  authorization divergence does not look like a bug, it looks like access.
  
  `principalFromSession()` bridges from the `auth` adapter contract: an absent
  or unverified session becomes `ANONYMOUS`, which `can()` refuses.
