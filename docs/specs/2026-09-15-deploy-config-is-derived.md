# `wrangler.toml` is a derivation of `[adapters]`, not a file you write

**Date:** 2026-09-15
**Status:** accepted

---

## Context

The Cloudflare adapter set's last unbuilt Cloudflare piece was "Workers, as
the `deploy` contract." Earlier specs deferred it with the observation that
`deploy` is *pipeline-shaped, not a runtime trait* — there is no
`Box<dyn Deploy>` to call at request time. True, but it left the question
of what `deploy = "cloudflare"` should actually *do* unanswered.

Looking at what a Cloudflare product had to write by hand answered it. The
`worker-cloudflare` capability shipped this, verbatim:

```toml
# [[d1_databases]]
# binding      = "MY_DB"
# database_name = "{{name}}"
# database_id  = "REPLACE_WITH_DATABASE_ID"
```

Every adapter built in the preceding phases reads a **fixed** binding name:
`D1Database` reads `env.DB`, `R2Storage` reads `env.BUCKET`,
`CloudflareQueue` reads `env.QUEUE`. A product following its own scaffold's
commented example bound `MY_DB` and got a Worker that threw
`"D1Database: no `DB` binding on env"` on its first query.

That is not a typo to fix. It is the platform's own founding defect,
occurring inside the platform: **one fact — which bindings this Worker needs,
under which names — was declared in two places, and the copy was wrong.**
`[adapters] database = "d1"` already says the product wants D1. The adapter
class already fixes the name. The `wrangler.toml` block adds no information;
it only adds a place to be inconsistent.

## Decision

`apps/worker/wrangler.toml` becomes a **derived artifact**, generated by a
new `fid-deploy` executor from `[adapters]` + a new `[deploy]` declaration,
gated by `fid derive --check` like every other artifact. `cloudflare` moves
from `candidates` to `implementations` on the `deploy` contract.

### The split, which is the whole design

| Derived from `[adapters]` | Declared in `[deploy]` |
|---|---|
| which binding blocks exist at all | the D1 database id (`wrangler d1 create`) |
| each binding's **name** (`DB`, `BUCKET`, `QUEUE`) | the R2 bucket name, the queue name |
| which secrets get named in a comment | `compatibility_date`, `route`, worker name |

The rule that generated the split: **if selecting a vendor implies it, it is
derived; if only the Cloudflare account knows it, it is declared.** A
database id is not derivable from anything — it is minted by Cloudflare and
handed back. A binding *name* is fully determined by the adapter that reads
it, and was only ever written down because nothing was generating the file.

Deselecting a vendor removes its block on the next derive. That is the
property that makes this worth building rather than a nicer template: the
file cannot drift from the selection, because it is not stored separately
from the selection.

### Secrets are named, never written

An adapter needing a secret (`turnstile` → `TURNSTILE_SECRET_KEY`,
`supabase` auth → `SUPABASE_URL`/`SUPABASE_ANON_KEY`) contributes a **comment
naming it and the `wrangler secret put` line to run**. Values never enter the
file. A generated file in a git repository is precisely the one place a
secret must not be, and the fact that the generator *knows which secrets are
needed* is exactly what makes it tempting to put them there — so the test
asserting no secret name ever appears outside a comment is a real guard, not
a formality.

### Validation names the field, and only when it applies

`compatibility_date` is required with no default: a date that moves changes
runtime behaviour under a product that did not ask it to, so "today" would be
the wrong default rather than a convenient one.

A `REPLACE_…` placeholder is an error **only for a vendor the product
actually selected**. Demanding a D1 id from a product that never selected D1
would make the seeded declaration unusable on the first derive — the same
failure the `brand` and `i18n` capabilities already learned to avoid by
seeding something valid.

## Why not the alternatives

**A runtime `Deploy` trait, for symmetry with the other contracts.** There is
nothing to call. Deployment happens in CI or at a terminal, not in a request
handler, and a trait with no caller is a shape invented for consistency's
sake. `deploy` stays the one contract whose vendor selection drives a
pipeline rather than a factory — and that asymmetry is now *documented by
what it produces* rather than merely asserted.

**A `fid deploy` command wrapping `wrangler deploy`.** Rejected: it would add
a second way to invoke a tool that already works, and the failure it would
own (a stale config) is better prevented than wrapped. `fid derive --check`
in CI plus `wrangler deploy` at the terminal covers it without the platform
holding the credentials or the exit codes.

**Generating only a fragment for the product to `include`.** Wrangler has no
include mechanism, so this was never available — but it is worth recording
that the whole-file generation is forced, not chosen, because it is the part
a product will notice: hand edits to `wrangler.toml` are lost.

**Leaving `worker-cloudflare`'s template file alone.** Rejected because the
template *was the defect*. Its comment now says bindings are derived, and
says plainly that its old examples were wrong and why — a scaffold that
quietly stops mentioning its own bug teaches nobody.

## Consequences

- `fid add deploy` takes ownership of `apps/worker/wrangler.toml`: a product
  that was hand-maintaining one will have its edits overwritten on the next
  derive. Anything that does not fit in `[deploy]` is a gap in the
  declaration worth reporting, and the SKILL says so.
- The Cloudflare adapter set item is down to two unbuilt pieces: Access
  (folded into Auth, shipped) and Workers AI (folded into the AI item, still
  parked). Workers-as-`deploy` is done.
- 11 end-to-end tests, including both halves of the property — a selection
  creates a binding, and an absent selection creates none.

## What this deliberately does not do

- **No Vercel or Fly implementation.** Both remain `candidates`. The
  executor refuses a non-Cloudflare `deploy` vendor by name rather than
  emitting a Cloudflare file for a Vercel product.
- **No secret management.** `wrangler secret put` stays a human's command.
- **No environments (`[env.preview]`, `[env.production]`).** Real, and the
  obvious next extension — but no product here has a second environment yet,
  and the shape of a preview environment's overrides is worth designing
  against a product that has one.
- **No KV or Durable Object bindings** — no contract selects either, so
  deriving them would mean inventing a declaration with no consumer.
