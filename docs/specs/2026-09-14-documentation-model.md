# The documentation model — one job per file, for the platform and every product

**Date:** 2026-09-14
**Status:** accepted

---

## Context

Nine Markdown files at the platform root and a tenth under `docs/`, with no
statement anywhere of what each was for. The results were predictable:

- **The principles existed in three places** — `MISSION.md` (authored),
  `AGENTS.md` (*"Core rules (from MISSION.md)"*), and the scaffolded
  `AGENTS.md.tmpl`. A test was added to hold two of them together, which caught
  drift without preventing it. **A gated duplicate is still a duplicate.**
- **`CLAUDE.md` and `AGENTS.md` overlapped on seven of eight sections** — layout,
  current phase, rules, tools, documentation, harvesting, build, what-not-to-do.
- **`PHASES.md` and `ROADMAP.md` both named what came next**, having briefly been
  coupled by number as well.
- **Products had no equivalent of any of it** — a scaffold got a `MISSION.md`
  stub and an `AGENTS.md`, and nothing else, so there was no answer to "how
  should a product be documented?"

## Decision

**One job per file. Where two files need the same content, it is generated, not
copied.**

| File | Its one job | Platform | Product |
|---|---|---|---|
| `README.md` | Front page for someone arriving cold | ✅ | ✅ |
| `MISSION.md` | **What this thing is for.** Platform: the thesis, the principles, the anti-goals. Product: what the product is for and who it serves | ✅ | ✅ |
| `ROADMAP.md` | What is **intended**, ordered by cost of delay | ✅ | ✅ |
| `PHASES.md` | What was **built** — the execution record | ✅ | optional |
| `AGENTS.md` | **The agent context.** Portable | ✅ | ✅ |
| `CLAUDE.md` | Claude Code specifics **only** | ✅ | — |
| `ARCHITECTURE.md` | How the layers fit together | ✅ | optional |
| `STACK.md` | Technology choices, enumerated | ✅ | optional |
| `IP-POLICY.md` | Licensing and disclosure boundaries | ✅ | — |
| `docs/specs/` | Decisions, append-only, date-stamped | ✅ | ✅ |
| `docs/guides/` | Guides for humans and agents | ✅ | optional |

### `MISSION.md` means the same thing in both, and that is the point

It answers *what is this for*. For the platform that is the thesis and the
principles; for a product it is the product's purpose. Same question, different
subject. The earlier confusion came from `MISSION.md` **claiming** it was copied
verbatim into every repository, which it never was.

### The principles are generated, not restated

- **The platform's `AGENTS.md` links to `MISSION.md`.** The file is right there;
  a summary would be a second declaration.
- **A product's `AGENTS.md` receives the text**, generated by
  `crates/fiducial-cli/build.rs`, which extracts the principles section at build
  time and fills a `{{principles}}` placeholder. A product cannot link to the
  platform's `MISSION.md` — its own says what the *product* is for — and it
  should not need the platform checked out to know the rules.

One place they are authored. One mechanism that puts them where they are needed.
The test that held the old copy honest is deleted: there is no copy left.

### `AGENTS.md` is the context; `CLAUDE.md` is the Claude-specific remainder

`AGENTS.md` is the emerging cross-vendor convention — **Codex, Copilot
Workspace and Cursor read it**, and so does Claude Code. So it holds everything
that is not vendor-specific: layout, rules, build commands, tools, what not to do.

`CLAUDE.md` holds only what has no meaning elsewhere — skills, subagents, MCP
servers, the plugin — and opens by pointing at `AGENTS.md`. It went from 200-odd
lines that restated `AGENTS.md` to 58 that do not.

**Products get no `CLAUDE.md` at all.** `fid new` scaffolds `AGENTS.md`, so a
scaffolded product is readable by any agent without a second file to maintain.

### `ROADMAP.md` is intent; `PHASES.md` is record

Different time directions, so both may exist. The redundancy was never their
coexistence — it was `PHASES.md` *also naming what came next*, which is the
roadmap's job. Removed.

`fid dash` reads exactly one: `ROADMAP.md`, then `PHASES.md`, then
`docs/ROADMAP.md`. The roadmap wins because a dashboard is forward-looking.
Asserted, so the two can never be counted together.

`fid new` scaffolds `ROADMAP.md` with the cost-of-delay table, so a product
inherits the ordering discipline rather than only the file.

## Consequences

- The platform's `ROADMAP.md` moved from `docs/` to the root, so platform and
  product agree on where it lives.
- `fid new` writes one more file.
- Changing a principle means editing `MISSION.md` and nothing else.
- Any agent that reads `AGENTS.md` — Claude Code, Codex, Copilot, Cursor — gets
  the same context, in the platform and in every product built from it.

## What this deliberately does not do

**No documentation site.** Markdown in the repository, rendered by GitHub,
versioned with the code. A docs site is a second place for documentation to live.

**No enforced `PHASES.md` for products.** Most products will not want a
phase-by-phase build record, and scaffolding an empty one invites it to rot.
